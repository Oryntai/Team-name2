# CQA — архитектура и контракт

Прототип Conversation Quality Analytics: ИИ оценивает работу оператора контакт-центра по настраиваемому
чек-листу, показывает обоснования со ссылками на реплики, принимает апелляции и решения проверяющего.

## Поток данных

```
API организаторов (GET ?group_id=…) ─┐
Загрузка JSON-файла ─────────────────┴─► импорт ─► SQLite (диалоги, исходные метки времени без изменений)
                                                     │
          чек-лист (версия) ─────────────────────────┤
                                                     ▼
                       маскировка ПДн (ИИН, карты, телефоны, e-mail, IBAN) — модель их не видит
                                                     ▼
                       судья: 3 независимых вызова модели на диалог (голосование), строгая JSON-схема из чек-листа
                       (Claude Haiku 5.5 по умолчанию; Sonnet; своя локальная модель — OpenAI-совместимый API)
                                                     ▼
                       по каждому критерию: ответ, обоснование, номера реплик-доказательств
                                                     ▼
                       итог — кодом по формуле чек-листа (N/A → перераспределение веса, округление 2 знака,
                       грубая ошибка — отдельная отметка) ─► карточка ─► апелляция ─► решение ─► пересчёт
```

Модель решает только смысл (что ответить по критерию и на какие реплики опереться). Код — только арифметику,
которую задаёт сам чек-лист, и хранение. Оценка содержит новые ответы модели и/или перенос из прошлой успешной
оценки той же моделью при совпадении отпечатка определения. Журнал хранит модель, версии, вызовы, время,
токены, цену и число перенесённых критериев. Готовых ответов по id диалога нет.

## Чек-лист (JSON)

```json
{
  "name": "Чек-лист качества чатов",
  "description": "Начальная конфигурация из PDF организаторов",
  "rounding": 2,
  "rules": ["общие правила для модели (памятка со стр. 3)", "..."],
  "criteria": [
    {"id": "01", "section": "Начало и понимание запроса", "title": "Установление контакта",
     "type": "bool", "weight": 10, "na": false,
     "yes": "оператор поздоровался на языке клиента и представился в первом ответе.",
     "no": "", "na_when": "", "steps": [], "guidance": ""},
    {"id": "04", "section": "Безопасность и решение", "title": "Корректная и полная консультация",
     "type": "scale", "weight": 20, "na": true, "yes": "оцените ответ или следующий шаг по шкале.",
     "na_when": "чат закончился до того, как клиент сформулировал запрос.",
     "steps": [{"value": 20, "text": "Все существенные вопросы закрыты…"}, {"value": 0, "text": "…"}]},
    {"id": "08", "section": "Грубые нарушения", "title": "Грубые ошибки", "type": "flag", "weight": 0, "na": false,
     "yes": "выявлено оскорбление клиента…", "no": "ни одно из трёх не выявлено."}
  ]
}
```

- `type`: `bool` (Да/Нет), `scale` (ступени `steps`, верхняя ступень = полный вес), `flag` (грубая ошибка: «Да» = нарушение, без баллов, `weight` = 0).
- `na`: разрешён ли N/A; `na_when` — условие (обязательно, если `na`).
- Секции — по полю `section` в порядке первого появления. `guidance` — необязательное пояснение для модели.
- Ответы везде строки: `"Да"`, `"Нет"`, `"N/A"`, ступень шкалы — `"15"`.
- Версии неизменяемы: правка в интерфейсе = новая версия (`parent_id` → от какой версии).

## Итог (`cqa/scoring.py`, правила стр. 2 чек-листа)

1. N/A — только где разрешён. 2. Да = полный вес, Нет = 0; шкала — только указанные ступени.
3. Баллы шкалы = вес × ступень / верхняя ступень. 4. N/A исключаем, веса применимых масштабируем до 100.
5. Итог округляем до `rounding` знаков (половина вверх, Decimal); нет применимых критериев с весом → итога нет.
Грубая ошибка — отдельная отметка, итог не обнуляет. Секция: баллы её критериев после перераспределения /
её максимум после перераспределения × 100. Пример из ТЗ: 02 и 03 N/A, 06 = 7, остальное Да / 20 → 93,08.

`score(config, answers) -> {"total", "gross", "gross_ids", "applicable_weight",
"criteria": {id: {"answer", "applicable", "weight", "points", "weight_eff", "points_eff"}},
"sections": [{"name", "ids", "points_eff", "max_eff", "percent"}]}`

## Судья (`cqa/judge`)

- Реплики нумеруются с 1 в порядке массива (метки времени не сортируем: бывают одинаковые). Модель видит
  `[n] timestamp speaker: text`, бот и системные события — как контекст.
- JSON-схема строится из чек-листа: объект `criteria` с ключом на каждый критерий, у ответа `enum` из допустимых
  значений этого критерия → модель физически не может вернуть недопустимый ответ.
  По критерию: `explanation` (коротко, по-русски, со ссылками [n]), `answer`, `evidence` (номера реплик; при «Нет» —
  участок, где действие ожидалось).
- `evaluate(record, config, provider, *, only=None) -> {"status", "error", "answers": {id: {"answer", "explanation", "evidence", "fingerprint", "reused_from"}},
  "provider", "model", "prompt_version", "latency_s", "input_tokens", "output_tokens", "cost_usd", "pii_masked", "raw"}`.
- Провайдеры: `haiku` (claude-haiku-5-5), `sonnet` (claude-sonnet-5-5), `local` (OpenAI-совместимый сервер:
  `CQA_LOCAL_BASE_URL`, `CQA_LOCAL_MODEL`), `fake` — только для тестов, в интерфейсе не показывается.

### Голосование (`cqa/vote.py`)

Оценка диалога — `CQA_VOTES` независимых вызовов (по умолчанию 3, параллельно; `votes` в `POST /api/runs`, 1–5).
По критерию — самый частый ответ; у шкалы при трёх разных ответах — медиана; при ничьей — ответ «медоидного» вызова
(чаще всех согласен с остальными). Обоснование и реплики — из вызова с итоговым ответом. У ответа — `votes`
(ответы всех вызовов) и `agreement` («2/3»); не единогласно → в карточке «модель не уверена». Стоимость и токены —
сумма вызовов; повтор попытки — только если упали все вызовы. В `results.json` голоса не попадают.
Замер на DEV (чек-лист v6): точность — на уровне среднего одиночного прогона, разброс меньше; ~9% решений не
единогласны — их и стоит смотреть проверяющему.

### Прецеденты (`cqa/precedents.py`)

Перед диалогом модель видит `CQA_PRECEDENTS` (по умолчанию 2) самых похожих утверждённых диалогов: разметку DEV
(`cqa/precedents/dev_reference.json`, медный эталон) и решения проверяющих по апелляциям (важнее разметки того же
диалога). Похожесть — TF-IDF и косинус по репликам клиента и оператора; оцениваемый диалог себя не берёт. Метки — только
для критериев, совпадающих с действующим чек-листом (у нового или изменённого критерия меток нет). В прецеденте нет
номеров реплик и бота, ПДн маскируются. Прецеденты одни для всех голосов, сохраняются в оценке (`evaluations.precedents`)
и видны в карточке. `PROMPT_VERSION` = p2. Замер: замысел авторов 91–93 → 93–95%, итог ближе к эталону.

### Инкрементальное применение

`only=["05"]` ограничивает схему и возвращаемые ответы этим списком. Системный промпт остаётся полным,
пользователь получает «Оцени только критерии: 05. Остальные не оценивай». Пустой `only` не вызывает модель.
`fake` строит ответ по схеме и тоже поддерживает частичную оценку.

Отпечаток — SHA-256 канонического JSON: `id`, `title`, `type`, `yes`, `no`, `na`, `na_when`, `steps`
(значения и тексты), `guidance`, общие `rules`, `PROMPT_VERSION`, имя модели. Вес и секция не входят.
`no` включён дополнительно к перечислению полей, поскольку этот текст тоже попадает в промпт.

В `incremental` при старте для каждого диалога фиксируется последняя успешная оценка той же моделью,
любой версии чек-листа (`run_items.previous_evaluation_id`). При совпадении сохранённого отпечатка
переносим исходный ответ, объяснение и доказательства, устанавливая `reused_from` в id этой оценки.
Остальные критерии оцениваем полным вызовом (в схеме весь чек-лист) и берём из ответа только изменённые: отдельный вызов на критерий на DEV хуже (92,5% против 94,2%). Нет прошлой оценки → оцениваем все критерии.
Нет изменений определений → создаём новую оценку без модели, с нулевой стоимостью и токенами.
Итог всегда считает существующий `scoring.score` по новой конфигурации. `full` переоценивает всё.
Повторы с `RETRY_PAUSES` сохраняются; вызовы, стоимость и токены суммируются по всем попыткам.
Решения проверяющего и апелляции не переносятся: они остаются у конкретной оценки.

Старые оценки без сохранённых отпечатков переоцениваются консервативно: совпадение определения доказать нельзя.
План — снимок текущей базы без запуска и записи; при новых оценках между планом и стартом он может измениться.

## База (SQLite, `var/cqa.db`)

```
settings(key PK, value)
datasets(id PK, source, fetched_at, total)
conversations(id PK, dataset_id, channel, language, transcript JSON, audio_url, imported_at)
checklists(id PK, name, version, parent_id, note, config JSON, created_at)
runs(id PK, created_at, finished_at, status, checklist_id, provider, model, total, done, failed, cost_usd, mode)
evaluations(id PK, run_id, conversation_id, checklist_id, created_at, provider, model, prompt_version, status, error,
            latency_s, input_tokens, output_tokens, cost_usd, answers JSON, pii_masked JSON, raw, total, gross,
            mode, evaluated JSON, reused JSON, model_calls)
run_items(run_id, pos, conversation_id, status, evaluation_id, error, previous_evaluation_id)
appeals(id PK, evaluation_id, criterion_id, comment, created_at, status open|confirmed|changed,
        new_answer, reason, decided_at)
```
Финальные ответы = ответы модели, поверх — решения проверяющего со статусом `changed`. Итог считается заново
из ответов при каждом чтении (`scoring.score`), в `evaluations.total` — исходный итог для списка.
`mode`: `full|incremental`; `evaluated` и `reused` у оценки — списки id критериев (запрошенных у модели сейчас
и перенесённых соответственно). При ошибках `evaluated` всё равно показывает запрошенные критерии.
`model_calls` — число попыток `judge.evaluate` с непустой схемой, включая неуспешные; внутренние повторы SDK
не видны этому счётчику. В `answers[id]` сохраняются `fingerprint` и `reused_from` (id оценки или null).
На старых базах отсутствующие колонки добавляются через `ALTER TABLE … ADD COLUMN`; историческим строкам
назначаются `mode=full`, пустые списки и `model_calls=0` (историческое число попыток неизвестно).

`POST /api/checklists/assist` принимает несохранённый черновик, включая проблемы формулировок (например, N/A без условия).
В модель передаются все критерии и общие правила, целевой критерий выделяется отдельно; ответ проверяется по строгой схеме.
Без `provider` используется модель из настроек (по умолчанию Haiku). Неизвестный номер критерия, неверная структура
или недоступный провайдер — `422`; ошибка провайдера или некорректный ответ модели — `502`; формат ошибок — `{"detail", "errors"}`.
Подсказка ничего не сохраняет: методист вставляет пояснение или заменяет условие N/A в редакторе и сохраняет новую версию обычной кнопкой.

`POST /api/checklists/try` валидирует несохранённый чек-лист через `checklist.validate` и оценивает не больше
трёх уникальных диалогов параллельно. По умолчанию сначала выбираются диалоги с прошлой успешной оценкой
той же моделью, по возможности разных языков; недостающие места заполняются диалогами без такой оценки.
Явный `conversation_ids` сохраняет порядок, после удаления дубликатов берутся первые три; пустой список — `422`.
По каждому диалогу через `incremental.partition` выбираются изменённые определения; если изменений нет
или прошлой оценки нет, оцениваются все критерии. Явный непустой `criteria` переопределяет выбор.
`previous_answer` — исходный ответ последней успешной оценки этой моделью, без решений по апелляциям.
Без `provider` используется модель из настроек. Неверный чек-лист, неизвестные диалоги/критерии, отсутствие
диалогов или недоступная модель — `422`; сбой провайдера/ответа модели — `502` с id диалога в ошибке.
Ошибки имеют формат `{"detail","errors"}`; при сбое одного диалога весь запрос возвращает ошибку.
`cost_usd` — сумма стоимости вызовов, `latency_s` — общее время параллельной оценки в секундах.
Чек-лист, прогоны и ответы не сохраняются; итог не рассчитывается. В редакторе кнопка «Проверить на 3 диалогах»
работает с черновиком, показывает сравнение ответов, обоснования, номера реплик и ссылки на карточки.

`GET /api/evaluations/{id}`:
```json

 "provider": "haiku", "model": "claude-haiku-5-5", "prompt_version": "p1", "created_at": "…",

 "latency_s": 8.9, "input_tokens": 2100, "output_tokens": 1500, "cost_usd": 0.00096,

   {"id": "04", "title": "…", "section": "…", "type": "scale", "weight": 20, "na": true, "allowed": ["20","15","10","5","0","N/A"],
```

В плане `evaluated`, `reused`, `definition_changed`, `weight_changed` у критерия — числа диалогов.
`definition_changed` учитывает также общие rules, версию промпта, новые критерии и отсутствие сохранённого
отпечатка в прошлой оценке; диалоги совсем без прошлой оценки вынесены в `without_previous`.
`weight_changed` — изменённый вес при совпавшем определении. `model_calls` плана — число диалогов,
для которых нужен вызов, без возможных повторов. В ответе прогона `evaluated` и `reused` — суммарные числа
критериев, `model_calls` включает неудачные попытки. Diff сравнивает исходные ответы и итоги, без апелляций;
добавление/удаление ответа обозначается null, неуспешные и незавершённые оценки не дают ложных изменений ответов.

## Аналитика

`cqa/analytics.py` ничего не записывает и не вызывает модель. Маршрут — `#/analytics`, компонент
`<cqa-analytics>`. Без `dataset_id` учитываются все наборы; без `checklist_id` — самая новая версия.
На каждый диалог берётся последняя успешная оценка выбранной версии (`MAX(id)`, `status='ok'`),
даже если после неё была неудачная попытка. Ссылки `#/c/<id>?e=<evaluation_id>` открывают именно эту оценку.

Сводка, гистограмма, срезы и нарушения используют финальные ответы с решениями проверяющего,
рассчитанные существующей `scoring.score`, как в карточке. Доля нарушений — среди ответов без N/A:
«Нет», ступень ниже максимума, для `flag` — «Да». Средний балл — `points_eff` после перераспределения,
без N/A и флагов. Итоги `null` не входят в среднее и гистограмму. Интервалы гистограммы — `[0,10)`,
`[10,20)`, …, `[90,100]`. Доли в JSON — 0…1; пустой знаменатель — `null`.

Расхождения считаются по исходным `answers.votes` (или `agreement`, если голосов нет).
Исторические ответы без этих данных не входят в знаменатель; `agreement_n` показывает его размер.
Совпадение (`criteria[].accuracy`: `rate`, `n`, `matches`) сравнивает **исходный** ответ модели с
`dev_reference.json`, включая N/A. Последнее решение проверяющего по совместимому определению
перекрывает разметку DEV, в том числе решение на предыдущей оценке. Подтверждение после изменения
сохраняет изменённый ответ. При смене определения/общих правил метка не используется; смена веса
или секции совместима. DEV — разметка моделей-судей, не эталон экспертов организаторов.

Апелляции считаются по всей истории выбранного набора и версии, включая предыдущие оценки:
`submitted`, `decided` (подтверждено или изменено), `changed`. Очередь содержит диалоги с грубой
ошибкой, расхождением голосов или итогом <60, с объединением причин без дублей; затем — 10% остальных
с округлением вверх, локальным `random.Random(26)` и стабильным порядком id.

Если `insights` отсутствует, `insights: null` и блок скрыт. Иначе берётся последний разбор,
совпадающий с выбранным `evaluation_id`; устаревший разбор другой оценки не подмешивается.
Тема агрегируется по диалогам; повторный код флага в одном диалоге считается один раз.

CSV использует финальные ответы, баллы `points_eff`, исходный вес, финальный итог и грубую ошибку;
голоса, номера доказательств и обоснование относятся к исходной модели. Отдельные колонки — ответ
модели и причина проверяющего. Неизвестное расхождение и отсутствующий итог — пустые ячейки.
Кавычки/переносы строк сохраняются; строки с префиксом формулы защищены апострофом при экспорте.

## Метрики звонка по меткам времени

`callmetrics.metrics(record)` вычисляется при чтении карточки, без записи в БД и без вызова модели.
В промпт, ответы модели и формулу итога не входит. Для канала, отличного от `voice call`, пустой
расшифровки или хотя бы одной не-ISO метки возвращает `null`. ISO с семью знаками дроби поддерживается;
точность расчёта — микросекунды, выдача секунд — до трёх знаков. Метки без зоны считаются UTC.
Исходные метки и порядок не меняются; отрицательные интервалы обнуляются с предупреждением `warnings`.

```json
{"estimated": true, "note": "оценка по меткам времени расшифровки, не по звуку",
 "duration_s": 70, "hold_s": 25,
 "holds": [{"start": "ISO", "end": "ISO", "start_n": 4, "end_n": 7, "duration_s": 25, "open": false}],
 "recording_pause_s": 5,
 "recording_pauses": [{"start": "ISO", "end": "ISO", "start_n": 5, "end_n": 6, "duration_s": 5, "open": false}],
 "speech": {"operator": {"seconds": 9, "share": 0.5422, "words_per_minute": 72.4},
            "client": {"seconds": 7.6, "share": 0.4578, "words_per_minute": 47.4}},
 "response_pauses": {"count": 3, "median_s": 10, "max_s": 12,
                     "long": [{"client_n": 2, "operator_n": 3, "duration_s": 12}]},
 "unknown_events": [{"n": 12, "timestamp": "ISO", "text": "CRM: статус обращения изменён."}], "warnings": []}
```

Длительность — от первой до последней реплики, включая системные события. Время каждой непустой
реплики клиента/оператора — минимум из интервала до следующей реплики и `число слов × 0,6 + 2` секунд;
последняя имеет нулевую длительность. Слова — последовательности букв/цифр, с внутренними дефисами
и апострофами. Доли (0…1) нормированы на сумму оценочного времени клиента и оператора, без бота,
системных событий и неотнесённых к речи интервалов. Темп — суммарные слова / суммарное оценочное
время × 60 только для реплик от трёх слов с положительным временем. Если времени нет, доля/темп — `null`.
Это оценка по меткам, не акустический замер; интонация не определяется.

Паузы ответа — разница **начал** соседних реплик `client → operator` в исходном массиве, включая
время речи клиента; бот/системное событие между ними прерывает пару. Порог длинных — строго больше 10 с.
Номера всех ссылок — позиции в массиве с 1, как в карточке. Медиана/максимум без пар — `null`.
Удержания и паузы записи учитываются независимо, даже при пересечении. События RU/KZ/EN распознаются
только у `system`, шаблоны собраны в `_EVENTS`. Повторное начало не открывает второй интервал;
конец без начала игнорируется. Незакрытый интервал заканчивается последней меткой (`open: true`,
`end_n: null`, `end` — метка конца разговора). Неизвестные события возвращаются в `unknown_events`.
Панель использует существующие `data-ref`/`data-seek` и `audio_offset`: секунды записи учитывают
паузы записи, поэтому не заменяются временем от начала звонка. Демо считает тот же контракт в `web/mock/callmetrics.js`.

## Интерфейс (`web/`)

HTML/CSS/JS без сборки и без внешних CDN. Каждый экран — веб-компонент с атрибутом `api-base`, чтобы его
можно было вставить веб-ресурсом в форму Dynamics 365: `<cqa-conversation-list>`, `<cqa-card conversation-id="…">`,
`<cqa-appeals>`, `<cqa-analytics>`, `<cqa-checklist-editor>`, `<cqa-journal>`; `<cqa-app>` собирает их в приложение (маршруты по `#`).
Роль («Оператор» / «Проверяющий») переключается в шапке, без входа: оператор подаёт апелляцию, проверяющий решает.
