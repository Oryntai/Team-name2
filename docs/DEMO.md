# Защита: сценарий на 5 минут

Порядок — как в ТЗ (стр. 4): интерфейс и диалог → оценка → апелляция → смена критерия. Говорим по-русски.

## Контрольный час (8.11, 11:00–12:00) — до защиты

Доступ к контрольному набору организаторы сообщат за час до стоп-кода. Всё — одной командой, ~25 секунд (репетиция 8.11 на 10
чатах — 24 с на рабочей базе, 34 с на пустой: там один раз переводится пул прецедентов DEV):

1. `uv run python -m cqa.results prod --group-id <group_id>` (дали файл — `--file ответ.json`; другая ссылка — `--url …`).
   Загрузка по API → оценка Haiku с повторами при сбоях → `results/prod/results.json` → проверка: ровно 10 записей,
   ID как в API, все правила приложения. Сервер может работать параллельно — прогон появится в журнале.
   Если в наборе есть нечитаемая запись — она в файле со status error и причиной (команда вернёт код 1 и напишет
   «Сдать: git add …»): по приложению это допустимо, пушить. «Не оценено моделью … НЕ пушить» — сеть или ключ:
   повторить ту же команду.
2. **Сразу** `git add results/prod/results.json && git commit -m "Результаты prod" && git push` — проверить, что файл
   виден на GitHub (локально или commit без push не считается). Всё остальное — после push.
3. Открыть 2–3 карточки контрольного набора: обоснования, реплики, итог. Если что-то явно не так — повторить шаг 1
   с `--fresh` и снова push (до 12:00).
4. Для показа (на results.json не влияет): «Аналитика» → набор контроля → «Разобрать диалоги» (резюме, темы, флаги,
   «как можно было»; ≈ $0,001 за диалог); казахские и английские чаты — «Перевести на русский» в карточке.
   Репетиция 8.11 03:10 (после поиска прецедентов по переводу): 10 чатов за 24 с, $0,035; с нарочно битой записью —
   19 с, 9 ok + 1 error с причиной.

## Подготовка (до выхода, ~10 минут)

1. База не пересоздаётся: в `var/cqa.db` действующий чек-лист, оценки DEV и контроля — те же, из которых собраны
   `results/*/results.json`. `uv run python -m cqa` → http://127.0.0.1:8000.
2. Если у контрольных чатов ещё нет разбора — «Аналитика» → набор контроля → «Разобрать диалоги (10)».
3. Вкладки заранее: «Диалоги»; карточки `p1-kz-008` (перевод), `p1-ru-022` (грубая ошибка), `p1-ru-025` (N/A);
   «Аналитика»; «Чек-лист». Роль в шапке — «Оператор».

## 0:00–1:00 · Интерфейс и диалог

- Первая фраза: «Microsoft уже встроила автооценку в Dynamics 365 — Quality Evaluation Agent. Мы сделали то же для
  чек-листа Freedom и добавили то, чего в его документации нет: апелляцию оператора, доказательство-реплику у каждого
  ответа и отметку, где модель не уверена; и всё это — на русском, казахском и английском».
- «Диалоги»: набор, язык, канал, итог, тема обращения под номером диалога. «Каждая оценка — живой вызов модели» (при смене критерия неизменённые ответы переносятся — это видно в журнале).
- `p1-kz-008`: транскрипт с исходными метками времени; «С переводом» — русский перевод под каждой казахской репликой
  (для проверяющего; модель оценивает оригинал, перевод нужен для поиска похожих диалогов). Оценивается только
  оператор: бот и события — контекст.

## 1:00–3:00 · Оценка

- `p1-ru-022`: плашка «Грубая ошибка» — перевод денег на личную карту, реплики-доказательства; итог не обнуляется.
- Значок критерия у реплики → окно: ответ, баллы, объяснение, «где этого не хватило» и «Как можно было» — совет
  оператору, как сказать эту реплику правильно.
- «Как посчитан итог»: баллы каждого критерия после перераспределения и формула — итог считает код, не модель.
- `p1-ru-025`: клиент ушёл, не сформулировав запрос → 04 «N/A» с причиной; вес перераспределён.
- «Разбор»: резюме, тема, настроение клиента «в начале → в конце», флаги «Недовольство», «Не решено».
- «Модель спрашивает» — критерий со значком «?»: три независимые оценки не совпали (5% решений, верны лишь в 58%, в них больше трети ошибок модели).
  Окно показывает вопрос к проверяющему, правило чек-листа, которое оценки поняли по-разному, и довод каждой позиции.
  Роль «Проверяющий» → «Верно» у нужного варианта → итог пересчитан, решение стало примером для похожих диалогов.
  Репетиция 8.11 на копии базы: `p1-kz-009`, 07 «Нет → Да», итог 92,31 → 100; вопрос ~7–10 с, ≈ $0,002.
- Если есть время — «Аналитика»: вопрос «Где операторы раскрывали данные без проверки личности?» → ответ со ссылками.

## 3:00–4:00 · Апелляция

- Роль «Оператор» → критерий (например, 07) → «Оспорить оценку» → причина «Неверная трактовка» + комментарий.
- Роль «Проверяющий» → «Апелляции»: справа ответ модели, реплики, причина и комментарий оператора → «Изменить» →
  новый ответ + причина → «Итог: было → стало» (на копии базы: 92,31 → 100).
- Решение проверяющего становится прецедентом: похожие диалоги дальше оцениваются с его учётом.

## 4:00–5:00 · Смена критерия (жюри называет, какой)

- «Чек-лист» → строка критерия → правка (название, тип, шкала, вес, N/A) → «Подсказка ИИ» → «Вставить в пояснение»
  (заменяет пояснение прежнего критерия; без этого редактор покажет жёлтое предупреждение).
  Прогон 7.11 на копии базы («Эмпатия» → «Персонализация»): подсказка ~10 с, проверка на 3 диалогах ~8 с,
  применение к 10 чатам — 15 с, $0,034 (30 вызовов, перенесено 70 ответов).
- Новый по смыслу критерий — «Проверить на 3 диалогах» (было → стало); переформулированный старый — «Сверить
  с утверждёнными» (совпало k из n).
- «Сохранить как новую версию» → «Применить к набору»: оценивается только новый критерий, остальное переносится
  («Перенесено из оценки №…»); контроль из 10 чатов — ~20 с. Сменить только вес — пересчёт без модели, мгновенно.
- Сразу под применением — «Вопросы к чек-листу» по набору. Оценки по новому критерию совпали во всех 10 диалогах —
  зелёная строка «изменён в этой версии: формулировка читается однозначно». Разошлись — «разошлись в N диалогах» →
  «Сформулировать вопрос» (~7 с) → вопрос к формулировке жюри с вариантами-правилами → «В пояснение» → «Сохранить» →
  «Применить» → «было N → стало M». Репетиция 8.11 (10 чатов второго DEV): «Персонализация обращения» — совпали во всех
  10; «Проактивность» — разошлись в 4, вопрос «засчитывать ли полезные сведения сверх вопроса или нужен следующий
  шаг», одно правило → было 4 → стало 3; каждое применение ~21 с, ~$0,05.
- Если жюри предлагает шкалу — попросить назвать ступени словами («0 — …, 5 — …, 10 — …»): на 10 пробных заменах
  да/нет-критерии совпали с независимой разметкой в 95%, размытые шкалы — в 70% (модель строже на ступень).
- Фраза: «Всю ночь мы сами искали, где чек-лист читается двояко. Теперь это делает система: где три её оценки
  расходятся, она не делает вид, что уверена, а задаёт вопрос — и ваш ответ становится правилом для всех диалогов».

## Цифры, если спросят

| | Обучающие 39 чатов | Отложенные 21 |
|---|---|---|
| База «всё выполнено» | 58,7% | 54,8% |
| Продукт: Haiku 5.5 + чек-лист v6f + прецеденты + голосование | 96,2% | 92,9%* |

\* Правки v6f сделаны по разбору ошибок на отложенных чатах, поэтому чистая проверка — 50 новых чатов вне DEV:
v6f 98,3% против 97,2% у v6.

Совпадение решений по критериям с «медным эталоном» (разметка судей Claude Opus; эталона организаторов для DEV нет).
Заложенные нарушения DEV — 17/17. Итог расходится с эталоном в среднем на 3–4 балла. С «замыслом авторов»
(101 решение по парам похожих чатов) — 96%.
Что пробовали и отбросили замером: Sonnet 5.5 на той же связке (замысел 93,6% против 94,1% у Haiku, в 12 раз
дороже), смешанное голосование Haiku + Sonnet (внутри шума), effort high/low, отдельный вызов на критерий,
«ИИ-суд» на спорных местах (добавлял шум), правила 04/02 в чек-листе v6e (DEV чуть хуже).

- **Где модель ошибается:** у каждого решения есть уверенность — согласие трёх оценок. Единогласно — 95% решений,
  они верны в 96,6%; разошлись — 5%, верны лишь в 58%, и в них больше трети всех ошибок (замер 8.11: 9 прогонов DEV,
  84 сочетания по 3 голоса, против меди). Система решает 95% сама и отдаёт человеку 5%, где сомневается. Поэтому в таких местах модель задаёт вопрос. На DEV
  43 спорных решения из 520 сводятся к вопросам о тех же серых зонах, что мы уточняли у организаторов: 02 «N/A или
  Да», 04 «передача на проверку без срока», 06 «снижать ли за реплику-нарушение 08», 07 «шаг назван раньше прощания».
- **Справедливость:** замена имён (казахские ↔ русские ↔ английские) и пола оператора меняет 2–3% решений — столько
  же, сколько простой повтор оценки (`lab/fairness.py`, 20 чатов, 54 варианта).
- **Цена:** оценка ≈ $0,004 (3 вызова Haiku), разбор диалога ≈ $0,001, перевод ≈ $0,0005, вопрос «Спросить ИИ» ≈ $0,01,
  вопрос модели к чек-листу ≈ $0,001–0,004 (повторный показ — из кеша, бесплатно);
  10 чатов контроля — ~20 секунд и ~$0,03.

## Если спросят

- **Чем это отличается от готовых систем?** Формат чек-листа ложится в структуру Microsoft QEA один к одному (таблица
  в ARCHITECTURE.md); сверх неё — апелляции, реплики-доказательства, «оценки разошлись», обучение на решениях
  проверяющих, своя модель без облака. Приём «пояснение к критерию + маленькая модель, дообученная на ответах большой»
  совпадает с опубликованным у Observe.AI (EMNLP 2024).
- **Почему не 100%?** Даже эксперты по качеству единодушны (5 из 7) лишь примерно в 60% случаев (Observe.AI,
  EMNLP 2024). Поэтому система показывает, где модель не уверена, и даёт оператору апелляцию. Наши 95% — против
  разметки моделей-судей, не экспертов: с цифрой экспертов их не сравниваем.
- **Не зависит ли оценка от имени оператора?** Проверили заменой имён (казахские ↔ русские ↔ английские) и пола в 20
  чатах: решения меняются в 2–3% случаев — столько же, сколько при простом повторе оценки (`lab/fairness.py`).
- **Почему не Decision-модель (ответ — вероятности по вариантам, без текста)?** Проверили 8.11 открытую Strands
  Decider 2B на тех же 60 чатах DEV, вопросы — из нашего чек-листа с пояснениями: 73,8% совпадения с эталоном против
  94,9% у продукта и ниже простой базы «самый частый ответ по критерию» (80,6%); её уверенность различает верные и
  ошибочные решения слабо (AUROC 0,61, у согласия наших трёх оценок — 0,67). Обоснований и реплик-доказательств
  такие модели не дают, а ТЗ их требует. Их главную идею — уверенность у каждого решения — берём: единогласные
  решения (95%) верны в 96,6%, спорные (5%) — в 58%, их видит человек.
- **Почему не модель считает итог?** Арифметика по ТЗ детерминирована: веса, N/A, округление — в коде, с автотестами.
- **Приватность.** ИИН, карты, IBAN, телефоны, e-mail, паспорта маскируются до отправки в модель (модель видит «[ИИН скрыт]»).
- **Без облака.** Провайдер «Своя модель · локально» — любой OpenAI-совместимый сервер (vLLM, llama.cpp, Ollama).
- **Встраивание в CRM.** Интерфейс — веб-компоненты; `embed.html?c=<id>` — карточка внутри формы Dynamics 365.
- **Реальная обработка.** Журнал: каждый вызов модели с временем, токенами и ценой; кеша по id диалога нет.
