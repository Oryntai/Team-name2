# Своя модель-судья локально (провайдер `local`)

Оценка диалогов без облака: открытая модель работает на ноутбуке, данные клиентов не покидают машину.
Продукт тот же: промпт и строгая JSON-схема строятся из чек-листа (`cqa/judge`), итог считает код по формуле.

## Запуск одной командой

```bash
bash lab/local/serve.sh
```

Скрипт при первом запуске скачивает модель (5,7 ГБ) в `~/models/cqa/` и поднимает OpenAI-совместимый сервер llama.cpp
на `http://127.0.0.1:8081` с нашим LoRA-адаптером. Затем в `.env` (или в окружении):

```
CQA_LOCAL_BASE_URL=http://127.0.0.1:8081
CQA_LOCAL_MODEL=qwen3.5-9b-cqa
```

и в интерфейсе выбрать модель «Своя модель · локально». Нужно: `brew install llama.cpp`, ~7–8 ГБ свободной памяти
(проверено на MacBook M1 Pro 16 ГБ). Варианты: `bash lab/local/serve.sh base` — та же модель без дообучения,
`bash lab/local/serve.sh gemma` — Gemma 4 12B; `CQA_LOCAL_SLOTS=8` — 8 диалогов параллельно вместо 4.

Голосование: продукт по умолчанию спрашивает модель трижды (`CQA_VOTES=3`). Для локальной модели ставьте
`CQA_VOTES=1`: она отвечает с temperature 0, и повторы совпадают полностью (два прогона на 21 чате — 168 из 168
решений), так что три голоса дали бы тот же ответ втрое дольше. Цифры своей модели ниже — один вызов на диалог.
`CQA_VOTES=1` задавайте в команде запуска своей модели, а не в `.env`: переменная общая, и облако тоже уйдёт в один голос.

## Что внутри

- **Модель:** Qwen3.5-9B (Apache 2.0), квантование Q4_K_M (5,7 ГБ, `unsloth/Qwen3.5-9B-GGUF`) + наш LoRA-адаптер
  `lab/local/adapters/qwen35-cqa/adapter.gguf` (58 МБ, r = 16).
- **Рантайм:** llama.cpp `llama-server` (сборка b11669), 4 параллельных слота, рассуждения выключены (`--reasoning off`).
  Схема чек-листа превращается в грамматику: ответ всегда валидный JSON с допустимыми ответами.
- **Дообучение («ставка»):** модель-ученик повторяет учителя на синтетических чатах. Выбрана попытка 4 — учитель
  сам продукт (Haiku 5.5 ×3 с прецедентами, `lab/local/relabel.py label` → `build`, описание — «Попытка 4» ниже);
  попытки 1–3 учились у Claude Sonnet 5.5 по шагам:
  1. `lab/local/synth.py gen` — Claude Haiku пишет новые чаты RU/KZ/EN в стиле DEV (бот AIM → эскалация → оператор)
     с нарушениями по плану; `lab/local/inject_gross.py` вставляет грубые нарушения, которые Haiku писать отказывается;
  2. `lab/local/synth.py label-batch` — учитель Sonnet оценивает их судьёй продукта (Batch API, полцены);
     30% — по изменённым чек-листам (замена критерия, другие веса, без пояснений), чтобы ученик читал чек-лист;
  3. `lab/local/synth.py build` — обучающие примеры в шаблоне Qwen (сверен байт в байт с llama-server);
  4. `lab/local/train_modal.py` — LoRA на Modal A100-80GB из кредитов, конвертация адаптера в GGUF той же сборкой llama.cpp.
  В попытках 1–3 DEV-чатов в обучении нет; в попытке 4 — 39 обучающих чатов DEV с утверждёнными ответами. Отложенные
  21 чат DEV и второй DEV (50 чатов) не входили ни в одну попытку — замер на них.

## Ограничения

- Скорость: на маке 10 контрольных чатов — ~5,5 мин (322 с, 4 слота, чек-лист v6f с прецедентами; облако — ~25 с).
  Почти всё время — чтение промпта: ~5 000 токенов на диалог (чек-лист с пояснениями, 2 прецедента, сам чат) идут
  со скоростью ~150 токенов/с на все слоты. Поэтому спекулятивное декодирование llama.cpp не помогает — оно ускоряет
  только генерацию (замер: по n-граммам 361–385 с вместо 322, принимается 3–20% подсказок; MTP-голов в этом файле
  модели нет). Для живой смены критерия на защите облако быстрее.
- Попытка 3 училась на промпте p1 и чек-листе v5 (учитель Sonnet на v5); на v6f с прецедентами (p2) перемерена без
  переобучения — таблица «На действующем чек-листе v6f». Попытка 4 учится уже на p2 и v6f.
- Казахский на отложенных — 82% (русский 89%, английский 95%): самый слабый язык.
- Медный эталон — мнение судей Opus, не эталон организаторов.
- Генератор Haiku отказывается писать оскорбления и «переведите мне на карту» даже для обучения — такие нарушения
  вставлены в 45 чатов кодом (`inject_gross.py`), разметил их тот же учитель.
